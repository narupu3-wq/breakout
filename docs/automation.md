# 定期レポートと戦略改善

2026-09-07にユーザー承認。Codexのこのタスクに定期処理を登録。

- 1時間ごと: レポート生成、直近1時間と累積の成績・稼働・異常のサマリー報告。
- 3時間ごと: 新しい証拠を使って戦略改善をレビュー。初回の定期実行時もレビューする。
- レビュー間隔は `reports/reviews/schedule-state.json` の `last_review_completed_at`
  （UTC Unix秒）から判定。データ不足で変更しない判断も完了したレビューとして記録する。
- 日次09:45/週次案は採用していない。現在の設定は上記の短い間隔。
- 回収目標は `docs/recovery-goal.md` を参照。2026-12-07までに月200 USDの継続収入とMac代回収を目指す。仮想利益と実受取を区別する。

## 毎時出力

S&P500も公開情報の監視対象に追加。`docs/sp500-monitor.md`に従い、価格基準日時・休場・欠損を記録する。
これは毎時の相場監視で、既存BTC/ETHの60秒収集・仮想売買とは別。Breakout気配未取得を明示する。

`python3 research.py report` に加え、`python3 hourly_report.py` を実行する。
毎時の数値は固定スクリプトの返す `report.json` を使用し、その都度PythonやSQLを組み立て直さない。
`reports/hourly/<UTC日時-一意ID>/` に `report.md`、`report.json`、実行スクリプトの凍結コピーを
まとめて原子的に保存する。既存レポートは上書きしない。失敗時は成功扱いせずエラーを報告する。
DBは読み取り専用の単一トランザクション。直近1時間は `(取得時刻-3600, 取得時刻]`。
欠損・不正・150秒超の気配で含み損益を評価せずnullと警告を返す（閾値は固定runのpoll秒×2.5）。
`review_due` はレビューの要否だけを表し、このスクリプトはレビュー完了時刻を更新しない。
S&P500欄は保存済み記録の参照で、新しい観測ではない。外部確認と監視記録の追記、
過去の発見・次の仮説・実受取状況の確認は定期タスクが別途行い、必要なら同じフォルダーへ
`analysis.md` を追記する。集計ファイルを後から書き換えない。
SQLite eventsのkind=close、payload.net_pnlを集計し、直近1時間の確定損益と累積を混同しない。
latest.jsonのbalanceは含み損益を含まない。含み損益はpositionのsymbol/qty/side/entryと、
該当symbolの最新snapshotのbid（long）またはask（short）から計算し、気配の観測時刻を明記。
最新paper runのheartbeatが古ければ停止/遅延として報告。自動でエラー記録やrunを消さない。

## 改善範囲

### BTC・ETH・S&P500の並行研究（2026-09-09）

ユーザー指定により3市場を並行して研究する。「学習」は公開データの分析、仮説の検証、再利用可能な知見の記録を指す。稼働中モデルの自動訓練や実注文を意味しない。

- BTC・ETH：固定版の常時収集と無発注観測を継続し、3時間レビューでは新しい証拠を銘柄別に分析する。既存候補の口座単位成績を保ち、銘柄別の取引結果は診断として区別する。
- S&P500：公開履歴、時刻付き価格、取引時間、費用・商品仕様を並行調査する。現在の取得不足を解消するため、次のレビューでは正規の無料データ取得手段を絞って検証する。取得不可の同じページを繰り返さず、障害と次の手段を記録する。実施条件は `docs/sp500-monitor.md` に従う。
- 各レビューにBTC・ETH・S&P500それぞれの「新しい証拠／不足／次の検証」を短く残す。証拠が増えない市場は変更なしとし、調査量を均等にするための反復作業は行わない。
- 比較は商品、時刻、期間、取引時間帯、コスト前提をそろえられる範囲で行う。過去探索とforward、市場別の損益と欠損を分離し、同時刻データのない市場間相関を推定しない。
- 過去分析とリアルタイム分析のおおむね半々、毎時報告、3時間レビュー、常駐改善版は同時1版までという運用を維持する。3市場の研究を理由にAI常駐呼び出しや追加課金を増やさない。

期間の判断は `docs/adaptive-validation.md` を優先。固定60日の一律待機から、成績・証拠に応じた短縮/延長へ変更。
旧固定版の機械判定と早期評価の可否を分けて報告し、収集や判断間隔が本当にボトルネックかも確認する。

過去チャート分析とリアルタイム無発注観測の分析を、おおむね半々の作業配分で行う。
過去側は相場局面・成功/失敗例・コスト込み再現性から仮説を作り、リアルタイム側は
事前記録した判断とその後の値動き・約定想定・損失を照合する。
約60秒の収集と15分足判断は常時継続する。配分を合わせるために取引数を増やしたり、
データ不足を隠して同じ分析を繰り返したりしない。過去とforwardの成績は別に報告する。
サマリーには過去側の発見・リアルタイムでの確認・次の仮説を簡潔に含める。

報告と改善は同じ定期処理内で行う。3時間経過前は通常レポートだけ。
論文・原著者の公開コードや検証記録を調査し、成功が報告された手法の根拠と不調期間を確認する。
手数料、未使用データでの評価、過剰適合、Breakout条件への適合と出典を記録する。
有望な仮説を1つだけ取り入れ、銘柄・相場条件・想定取引数を限定した無発注実験で基準版と比較する。
宣伝、第三者の個別売買シグナル、小標本の利益を成功の証明にしない。新しい検証課題のない資料再調査は避ける。
改善は毎回必ずコードを書き換える意味ではない。少数の勝敗、サンプル不足、同じ証拠の場合は見送る。
根拠があるときは一度に変更1件を `experiments/<version>/` に実装し、独立DBで検証する。
固定研究版のソース/config/DB/ゲートを変更しない。必要なデータはSQLite backup API等で
読み取りスナップショットを作る。動作中SQLiteを単純ファイルコピーしない。
基準版と改善版のデータを混ぜない。候補コードのROOT/既定DB/レポート出力先が独立していることを確認する。
過去比較は探索、改善後に蓄積するデータがforward。過去データで改善したことを本番適合の根拠にしない。
テスト・コスト2倍・損失条件の確認を通した有望候補のみ無発注観測を開始する。
自動新設する常駐改善版は同時1版まで。実注文・自動昇格・購入・追加課金は対象外。

## 稼働条件

定期処理はCodexの利用可能な実行環境・権限・利用枠に依存する。
Mac/Codexの停止等による遅延を隠さず、未実行分を実行済みとみなさない。
市場収集プログラムの約60秒/判断15分足という間隔と、レポート・改善の間隔は別。

## 遅延診断（hourly-report-v2）

毎時の同一読み取りスナップショットから、累積と直近1時間の観測間隔、60秒待機からの
超過分、足確定から条件確認・シグナル判断までの秒数（件数・平均・p95・最大）を集計する。
銘柄・足単位で候補の重複を除外。初回起動時の古い足も含め、120秒超のシグナルを別集計する。
150秒超の間隔はheartbeat間で1回と数え、候補別data_gapを合算しない。
取得エラーの件数・内容と、それを挟んだ観測間隔数も表示する。
実際の待機は処理完了後60秒。超過分はAPI通信時間ではなく、処理・スケジュール等も含む。
API別所要時間、成功前の再試行、判断計算の実終了時刻、実注文の遅延は未計測。
エラーの同時発生は因果関係の証明ではない。損益影響や取得間隔変更の判断は別の検証が必要。
戦略コード・設定・稼働runは変更せず、保存するreporter.pyだけで集計を再現できる。

## 独立リアルタイム観測

`experiments/realtime-v1/README.md` のKraken WebSocket観測を追加。
毎時レビュー時は `node experiments/realtime-v1/monitor.mjs status` で鮮度・受信件数・拒否・急変・容量を確認する。
基準版の成績と合算しない。AI呼び出し・仮想売買を行わない検知実験。
欠損の履歴自動補完は未実装。詳細は30日後に検証付きの可逆圧縮で保持する。
